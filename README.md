# CoCIS Smart Control and Monitoring System

ESP-IDF firmware for the Makerere University CoCIS smart access and room-lighting coursework. One ESP32 runs entrance control and two logical room-terminal tasks. It includes separate entry/exit RC522 readers, two PIR/light channels, an administrator panel, room-status messaging, and Wokwi door servos.

## Hardware mapping

| Function | ESP32 GPIO | Wokwi part |
|---|---:|---|
| Shared SPI clock | 18 | Both MFRC522 readers and microSD |
| Shared SPI MISO | 19 | Both MFRC522 readers and microSD |
| Shared SPI MOSI | 23 | Both MFRC522 readers and microSD |
| Entry RFID chip select | 32 | Entry MFRC522 |
| Exit RFID chip select | 33 | Exit MFRC522 |
| Entry / exit door servos | 13 / 14 | Wokwi servos; RC522 reset wires are not used |
| SD chip select | 5 | microSD card |
| Lecture Room 1 PIR / light | 27 / 2 | PIR 1 / yellow LED 1 |
| Lecture Room 2 PIR / light | 26 / 4 | PIR 2 / yellow LED 2 |
| Entry-door indicator / exit-door indicator | 16 / 17 | Green LED 1 / green LED 2 |
| Emergency exit pushbutton | 25 | Pushbutton to GND, internal pull-up enabled |
| Emergency buzzer | 15 | Wokwi buzzer; pulsed 2 kHz tone during button press |
| DS1307 SDA / SCL | 21 / 22 | RTC module |
| Admin LCD SDA / SCL | 21 / 22 | 16x2 I2C display; shared with RTC |
| Admin keypad | I2C address 0x20 | 4x4 keypad connected through MCP23017 expander |

The yellow LEDs represent the lecture-room lights and are controlled by PIR motion, not by RFID scans. The green LEDs and servos represent entry/exit door outputs. RFID scan messages should appear in the serial terminal whether the tag is accepted or denied.

## Build and run

This project uses PlatformIO with the ESP-IDF framework. From the project root, build the `esp32dev` environment with:

```sh
pio run
```

The firmware outputs are `.pio/build/esp32dev/firmware.bin` and `.pio/build/esp32dev/firmware.elf`, which are the paths configured in `wokwi.toml`. Open the project with the Wokwi extension and start the simulator after a successful build.

## Custom RC522 driver

The firmware uses its own SPI-level RC522 driver instead of the bundled reader library. It initializes both readers, sends REQA and anticollision commands, checks the four-byte UID block check character, and serializes access to the shared RFID/SD SPI bus. An empty FIFO after a no-card poll is treated as a normal timeout; actual SPI communication failures are reported once per reader until a successful read.

This implementation currently handles four-byte UIDs (including the configured Wokwi Blue Card). Longer UID cascade levels are not implemented. The updated driver was tested in Wokwi on 31 October 2026: both readers detected and granted the configured card, and no invalid-size errors appeared during empty-reader polling or after taps. Physical reader hardware has not been tested.

## RFID demonstration

The Wokwi diagram's configured card UID is `A1:B2:C3:D4`; the firmware normalizes this to `A1B2C3D4`. The demo authorization list also contains `DEADBEEF` and `CAFEBABE`.

Expected serial messages for an authorized entry scan include:

```text
RFID entry reader detected UID A1B2C3D4
ACCESS GRANTED at entry for UID A1B2C3D4
Door entry released for UID A1B2C3D4
```

Scan the same UID at the entry reader a second time without first exiting: the scan should be denied because that UID is already recorded inside. To demonstrate exit, scan the same UID at the exit reader. A valid exit should pulse the exit-door indicator, remove the UID from the inside list, and append an EXIT log.

The serial console provides:

- `help`
- `status`
- `logs`
- `scan in A1B2C3D4` and `scan out A1B2C3D4` for logic testing without touching a physical reader
- `login 2468` to authenticate for five minutes in the classroom demo
- `schedule 07:00 18:00` to set the entry/exit access window
- `time 09:00` to set the demonstration clock
- `logout`

The default access window is 07:00-18:00. Overnight windows are supported as well, for example `schedule 20:00 06:00`. Equal start/end times are rejected as an invalid schedule. Administrative schedule and time changes require a login first.

The shared serial/keypad authentication locks login for 30 seconds after three consecutive wrong PINs. The console help shows only the `login <PIN>` syntax, not the configured PIN. Building occupancy is capped at 64 authorized tags through the single `MAX_OCCUPANTS` setting.

### Visible Wokwi administrator panel

The diagram includes a 16x2 I2C LCD and a 4x4 membrane keypad. The LCD shares the RTC I2C bus; the keypad connects through a simulated MCP23017 I/O expander at address `0x20`. Wokwi downloads that custom-chip dependency from GitHub when opening the diagram.

- On the home screen, press `A`, enter the demo PIN `2468`, then press `#`.
- In the admin menu, `A` sets opening/closing times, `B` displays access status and occupancy, `C` sets the demonstration clock, and `D` logs out.
- Enter times as four digits (`HHMM`) and press `#` to submit each value. The same schedule validation and persistence used by the serial console applies.
- On the home screen, press `#` to view status. The serial console remains available for `logs`, testing, and fallback if the panel cannot initialize.
- A scan displays `WELCOME`, `GOODBYE`, or `ACCESS DENIED` with a brief reason. During the final ten minutes of an open schedule, the home screen warns how many minutes remain.

## Room terminal messages

Room 1 and Room 2 each run in a separate FreeRTOS task. Each task controls its own PIR/light pair and publishes versioned occupancy/light status messages to a FreeRTOS queue. An entrance-side task consumes those messages; `status` reports each room terminal as online or offline based on recent updates.

These are logical terminals on the same ESP32, not three separate ESP32 boards or a wireless/network link. The queue demonstrates synchronized inter-task communication in the single-board Wokwi design; it does not demonstrate inter-board communication.

## Storage and recovery

Access records are maintained in the ESP32 NVS store and written to `/sdcard/access.csv` when the SD card is mounted. If the SD card is missing or fails to mount, NVS is used as the access-log fallback. The NVS log is a rolling buffer containing the most recent 24 events; the SD CSV log can retain a longer history. Occupancy snapshots use `MAX_OCCUPANTS` (64); an older saved 16-person snapshot is migrated at startup.

The emergency-egress button opens the exit servo independently of RFID, schedule, and administrator authentication. It is intentionally not restricted: anyone inside must be able to leave, including after hours. Pressing it also activates the pulsed audible buzzer and prints an emergency message; the buzzer stops when the button is released. Normal RFID exit scans remain subject to the configured schedule. In a real installation, put the release on the inside/egress side only, use a monitored break-glass cover if appropriate, and never let a cover or software delay escape. The Wokwi buzzer, LEDs, and servos are simulation indicators, not certified alarm or door hardware.

## Static project-integrity check

From this directory, run:

```sh
python3 tests/verify_static.py
```

The script checks project layout, diagram JSON/wiring, custom RC522 operations, shared-SPI safeguards, access controls, LCD messaging, servos, room queues, and selected firmware invariants. A passing static check alone is not proof that the firmware compiles or that the Wokwi simulation has run; the latest interactive test results are recorded below.

## Verification checklist

1. On startup, the serial terminal reports whether the RTC, SD card, both RC522 readers, the room tasks, and admin panel initialized successfully.
2. Use **Tap** on each Wokwi Blue Card reader; confirm the custom driver detects the configured UID, produces an access decision, and actuates the matching green indicator and servo.
3. Scan the same UID at entry again; confirm a duplicate-inside denial and no new granted event.
4. Scan that UID at the exit reader; confirm an exit detection message, exit servo/indicator movement, and an EXIT record.
5. Type `status` and `logs`; confirm occupancy, room-terminal online status, and event history agree with the scans.
6. Trigger PIR 1 and PIR 2 independently; confirm each corresponding yellow LED turns on, then turns off after approximately 10 seconds without further motion.
7. Type `login 2468`, set the clock outside the schedule, and scan a valid UID; confirm access is denied and the door indicator remains off. Restore the time/schedule before continuing.
8. Press the emergency-egress button outside access hours; confirm the exit-door indicator and pulsed buzzer activate without admin login, then stop when released.
9. Disconnect/remove the SD card in a test run; confirm the firmware reports an NVS fallback and still records access events.
10. Use serial and keypad login to enter three wrong PINs; confirm both interfaces share a 30-second lockout. Then use the keypad/LCD to log in, change the schedule and clock, view status, and log out.
11. Restart the simulator; confirm persisted occupants, schedule, and NVS access history are restored.
12. Set the clock within ten minutes of closing; confirm the LCD countdown warning appears and clears when the window closes.

### Latest interactive Wokwi test (31 October 2026)

The post-fix simulation verified entry and exit card scans with no `ESP_ERR_INVALID_SIZE` polling errors, duplicate-entry denial and occupancy updates, both PIR/light timeout paths and room-queue messages, keypad/LCD login and status, the 30-second PIN lockout, emergency egress/alarm activation and release, SD event-log reads, and the closing warning at 17:55. The demo clock was restored to 12:05 afterward.

Out-of-schedule RFID denial, SD-card failure fallback, NVS migration across restart, and physical hardware remain untested.

## Scope and honest limitations

- The project builds the firmware image at `.pio/build/esp32dev/firmware.bin`; Wokwi loads that image and the matching ELF through `wokwi.toml`. The lecturer approved repository/archive submission instead of a Wokwi share link; the group plans to share the project archive through Google Drive.
- The current design centralizes room and entrance control on one ESP32, following the lecturer's clarification for the demonstration. Room tasks communicate with the entrance task through a local FreeRTOS queue, not a wireless link or separate controllers.
- PIR-based occupancy is motion-based, so it is a useful classroom-lighting approximation rather than a true people counter. The RFID list counts authorized tags, not visitors who enter without using a tag.
- For a physical hardware build, verify the RTC module's I2C pull-up voltage. A DS1307 module powered from 5 V may pull SDA/SCL toward 5 V; do not connect 5 V logic directly to ESP32 GPIOs. Use a 3.3 V-compatible interface or suitable level shifting.
- The default PIN and demo UIDs are coursework credentials, not production-grade access security. Change credentials and adopt stronger identity verification before real deployment.
- The emergency-egress control is a life-safety override, not an anti-intrusion feature. A person already inside must not be trapped to enforce hours; protect the exterior against unauthorized entry and monitor emergency-release use instead.
